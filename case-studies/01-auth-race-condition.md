# CS-01 · login ล้มแบบสุ่ม 1 ใน N ครั้ง — race condition ระหว่าง session สองเส้น

> **สรุปสั้น:** E2E จับบั๊กที่ manual test ไม่มีทางเจอ เพราะมันไม่ล้มทุกครั้ง
> รากคือ sign-in สองเส้นแข่งกัน ไม่ใช่เทสที่ flaky

| | |
|---|---|
| **ระบบ** | แพลตฟอร์มจองคิวบริการ (Angular + Firebase, ใช้งานจริงบน production) |
| **บทบาทของผม** | ออกแบบและเขียน E2E ทั้งชุด + วิเคราะห์หาสาเหตุ + แก้โค้ด |
| **เครื่องมือ** | Playwright, Firebase Auth, Cloud Functions |

## บริบท

ระบบกำลังเพิ่ม role ใหม่ (เจ้าหน้าที่ประกัน) ผมเขียน Playwright E2E ครอบ flow นี้ก่อนขึ้นจริง

## อาการ

เทส login **ผ่านบ้างไม่ผ่านบ้าง** ทั้งที่โค้ดเทสเหมือนเดิม — ตอนล้มได้ **HTTP 403 `auth/not-phone-verified`** จาก Cloud Function ตอนลองด้วยมือก็ล้มบ้าง แต่ลองซ้ำอีกทีก็ผ่าน

จุดที่ตัดสินใจถูกตั้งแต่ต้น: **ไม่ใส่ retry แล้วปล่อยผ่าน** เทสที่ล้มแบบสุ่มมีสองความเป็นไปได้เสมอ — เทสไม่นิ่ง หรือ**ระบบไม่นิ่ง** ถ้าใส่ retry ทันทีจะไม่มีวันรู้ว่าเป็นอันไหน

## วิธีตามรอย

1. **แยกให้ได้ก่อนว่าเป็นของใคร** — ยิง login ด้วยมือซ้ำๆ จนล้มได้จริง → พิสูจน์ว่าไม่ใช่ปัญหาของเทส
2. **ดูจากฝั่ง server ว่ามันเห็นอะไร** — error บอกว่า `sign_in_provider` ที่ token ส่งมาเป็น `anonymous` ทั้งที่ผู้ใช้เพิ่งกรอกรหัสผ่าน
3. **ไล่ว่าใครเป็นคนเรียก sign-in** — เจอว่ามีสองเส้นทางที่เรียกได้: `ensureAnonymousAuth()` (ให้ผู้เข้าชมทั่วไปอ่านข้อมูลสาธารณะได้) และ `signInWithEmailAndPassword()` (ตอน login จริง)

## สาเหตุราก

สองเส้นนี้ทำงาน **ขนานกัน** และไม่มีใครรอใคร

```
ผู้ใช้กด login
├─ ensureAnonymousAuth()  ──────────────► signInAnonymously ──► resolve (ช้ากว่า)
└─ signInWithEmailAndPassword() ──► resolve (เร็วกว่า)
                                              ▲
             session ของ password ถูก anonymous ทับทิ้งตรงนี้
```

ถ้า `signInAnonymously` เผอิญ resolve **ทีหลัง** มันจะทับ session ที่ login สำเร็จไปแล้ว พอเรียก Cloud Function ต่อ token ที่ส่งไปจึงเป็น anonymous → server ปฏิเสธถูกต้องตามกฎ

เพราะขึ้นกับว่าใคร resolve ก่อน มันจึงล้ม**เป็นบางครั้ง** และล้มบ่อยขึ้นบนเน็ตช้า

**ขอบเขตกระทบกว้างกว่าที่เห็น:** ตอนแรกดูเหมือนเป็นปัญหาของ role ใหม่ แต่จริงๆ **กระทบทุก role** — แค่ไม่มีใครสังเกตเพราะคนมักลอง login ซ้ำแล้วก็เข้าได้

## การแก้

เรียงลำดับให้ชัด แทนที่จะปล่อยให้แข่งกัน — `signInWithPassword()` **รอ** `ensureAnonymousAuth()` ให้จบก่อน แล้วค่อย sign in ทับ และ `ensureAnonymousAuth()` เช็ค `currentUser` ซ้ำอีกรอบก่อนยิง เพื่อไม่ให้ sign in ทับผู้ใช้ที่ login อยู่แล้ว

## การยืนยัน

- เทส E2E ของ flow นี้ 6/6 ผ่านบน production จริง (ไม่ใช่ mock)
- รันซ้ำหลายรอบเพื่อยืนยันว่าไม่ได้แค่ "บังเอิญผ่าน"

## บทเรียนที่เอาไปใช้ต่อ

- **เทสที่ล้มแบบสุ่ม ไม่ได้แปลว่าเทสห่วยเสมอไป** ต้องแยกให้ออกก่อนว่าเป็นเทสหรือระบบ การใส่ retry เป็นปฏิกิริยาแรกคือการกลบบั๊ก race ที่กระทบผู้ใช้จริง
- **error message ของ server คือหลักฐานชิ้นสำคัญที่สุด** `sign_in_provider: anonymous` บอกได้ทันทีว่าปัญหาอยู่ที่ "ตัวตนตอนยิง" ไม่ใช่ "รหัสผ่านผิด"
- **บั๊กที่เจอใน flow ใหม่ อาจไม่ใช่บั๊กของ flow ใหม่** ต้องถามเสมอว่าขอบเขตกระทบจริงกว้างแค่ไหน
