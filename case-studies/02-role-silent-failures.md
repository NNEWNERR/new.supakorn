# CS-02 · เพิ่ม role ใหม่ 1 ตัว พังเงียบ 6 จุด

> **สรุปสั้น:** การเพิ่มสิทธิ์ผู้ใช้หนึ่งประเภท ไม่ใช่งานที่จบในไฟล์เดียว
> จุดที่พังหนักที่สุดไม่ใช่หน้าใหม่ แต่คือ "กด refresh แล้วหลุด login"

| | |
|---|---|
| **ระบบ** | แพลตฟอร์มจองคิวบริการ (Angular + Firebase + Cloud Functions) |
| **บทบาทของผม** | วางแผนทดสอบ, เขียน E2E, ไล่หาจุดพัง, แก้โค้ด |
| **เทคนิคที่ใช้** | state-transition testing, decision table (role × หน้าจอ), negative testing |

## บริบท

ระบบมี role อยู่ 5 แบบ ต้องเพิ่มแบบที่ 6 (เจ้าหน้าที่ประกัน) ที่เห็นข้อมูลได้จำกัดและมีหน้า export รายงานของตัวเอง

## สิ่งที่พบ

ไม่ใช่บั๊กเดียว แต่เป็น **defect class เดียวกันซ้ำ 6 จุด**: มีโค้ดหลายที่ที่ **hard-code รายชื่อ role ไว้เอง** และไม่มีใครรู้ว่ามีกี่ที่

จุดที่อันตรายที่สุดคือจุดที่ 6 — ฟังก์ชัน `restoreSession()` ที่ใช้ตอนเปิดแอปใหม่ มี allow-list เขียนตายไว้ว่า role ไหนถือว่า "login อยู่"

```
ผู้ใช้ login สำเร็จ ──► ใช้งานได้ปกติ ✅
       │
       └─► กด refresh / เปิด deep link
              └─► restoreSession() ไม่เห็น role นี้ใน allow-list
                     └─► ถือว่ายังไม่ login → guard เด้งออกหน้า login ❌
```

**ทำไมถึงหลุดการทดสอบง่าย:** ทดสอบตามปกติคือ login แล้วไล่กดทีละหน้า ซึ่ง**ผ่านหมด** ต้องมีคนตั้งใจกด refresh กลางทาง หรือเปิดลิงก์ตรงจาก bookmark ถึงจะเจอ — ซึ่งเป็นสิ่งที่ผู้ใช้จริงทำทุกวัน

## การแก้

แทนที่จะไล่เติมชื่อ role ใหม่ลงในทั้ง 6 จุด (ซึ่งจะพังอีกรอบตอนมี role ที่ 7) ย้ายไปใช้ **แหล่งความจริงเดียว** — ประกาศรายการ role ที่ถือว่า login แล้วไว้ที่เดียว พร้อมฟังก์ชันตรวจสอบตัวเดียว แล้วให้ทุกจุดเรียกใช้อันนั้น

## การยืนยัน

- E2E 7 เคส ครอบตั้งแต่ login, สิทธิ์การมองเห็นข้อมูล, การ export, จนถึง **เคส refresh กลางทาง** โดยเฉพาะ
- รันจริงบน production 6/6 ผ่าน

## บทเรียนที่เอาไปใช้ต่อ

- **"เพิ่ม role" ไม่ใช่ story ขนาดเล็ก** ต้องทำ decision table role × (หน้าจอ / API / กฎฐานข้อมูล / การ restore session) ก่อนประเมินงาน
- **เคสที่คนลืมทดสอบที่สุดคือ refresh และ deep link** เพราะการทดสอบด้วยมือมักเป็น flow ต่อเนื่องที่ไม่มีใครรีเฟรชกลางทาง — แต่ผู้ใช้จริงทำ
- **บั๊กที่ซ้ำหลายจุด อย่าแก้ทีละจุด** ถ้าแก้ 6 จุดโดยไม่รวมศูนย์ บั๊กเดิมจะกลับมาใหม่ในรอบถัดไป ข้อเสนอของ QA ควรรวมถึง "แก้ยังไงไม่ให้กลับมาอีก" ไม่ใช่แค่ "ตรงนี้ผิด"
