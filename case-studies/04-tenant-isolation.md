# CS-04 · กันข้อมูลข้ามองค์กรรั่ว — ทดสอบ 3 ชั้น เจอบั๊กครบ 3 ชั้น

> **สรุปสั้น:** ระบบ multi-tenant ที่ลูกค้าหลายเจ้าใช้ฐานข้อมูลก้อนเดียวกัน
> "อ่านข้อมูลของคนอื่นไม่ได้" ไม่ใช่ feature แต่เป็นเงื่อนไขขั้นต่ำ
> และต้องพิสูจน์ทุกชั้น ไม่ใช่เชื่อชั้นใดชั้นหนึ่ง

| | |
|---|---|
| **ระบบ** | แพลตฟอร์มจองคิวแบบ multi-tenant (Firebase, ลูกค้าหลายองค์กรใช้ฐานข้อมูลร่วมกัน) |
| **บทบาทของผม** | ออกแบบชุดทดสอบความปลอดภัย, เขียน rules test, ไล่หาบั๊ก, ตรวจซ้ำหลังแก้ |
| **เทคนิคที่ใช้** | negative testing, decision table (ผู้ใช้ × ข้อมูล × การกระทำ), defense in depth |

## โจทย์

ระบบเปลี่ยนจาก "ลูกค้าเจ้าเดียว" เป็น "หลายองค์กรใช้ระบบเดียวกัน" โดยข้อมูลทุกก้อนติดป้ายว่าเป็นขององค์กรไหน คำถามที่ต้องตอบให้ได้ก่อนเปิดใช้งาน: **ถ้าผู้ใช้ขององค์กร A พยายามอ่านหรือแก้ข้อมูลขององค์กร B จะเกิดอะไรขึ้น**

คำถามนี้ตอบด้วยการกดผ่านหน้าจอไม่ได้ เพราะหน้าจอไม่มีปุ่มให้กดอยู่แล้ว — **ต้องยิงตรงไปที่ฐานข้อมูลและ API**

## วิธีทดสอบ

**ชั้นที่ 1 — กฎความปลอดภัยของฐานข้อมูล** เขียน rules test รันกับ Firebase emulator ครอบเป็นเมทริกซ์: ผู้ใช้องค์กร A × ข้อมูลองค์กร A/B × อ่าน/เขียน/ลบ

ปัจจุบันชุดนี้มี **91 เคส** แบ่งเป็น 4 กลุ่ม — การแยกข้อมูลระหว่างองค์กร, การแยกข้อมูลของระบบรุ่นเก่า, สิทธิ์ผู้ดูแลระดับแพลตฟอร์ม และความเข้ากันของชื่อฟิลด์รุ่นเก่า/ใหม่

**ชั้นที่ 2 — API ฝั่ง server** ยิงตรงไปที่ endpoint ด้วย token ขององค์กร A แต่ระบุ id ข้อมูลขององค์กร B

**ชั้นที่ 3 — หน้าเว็บ** ตรวจว่าแอปส่งบริบทองค์กรไปถูกตั้งแต่ก่อนเริ่มดึงข้อมูล

## สิ่งที่พบ — บั๊กชั้นละหนึ่ง

**ชั้นหน้าเว็บ:** แอปเริ่ม subscribe ข้อมูล **ก่อน** ที่บริบทองค์กรจะถูกตั้งค่า — คำขอชุดแรกจึงออกไปโดยไม่มีป้ายว่าเป็นขององค์กรไหน

**ชั้น API:** endpoint สำหรับแก้ไขการจอง **ไม่ได้ตรวจสิทธิ์เลย** — ใครถือ token ที่ login แล้วก็แก้ของใครก็ได้ ขอแค่รู้ id

**ชั้นกฎฐานข้อมูล:** ข้อมูลรุ่นเก่ากับรุ่นใหม่ **เขียนชื่อฟิลด์องค์กรคนละแบบ** (`projectId` กับ `project_id`) กฎที่อ่านแค่ชื่อเดียวจะมองไม่เห็นป้ายของอีกฝั่ง — เอกสารที่ไม่มีป้ายในสายตาของกฎ คือเอกสารที่กฎตัดสินใจผิดได้

จุดสุดท้ายนี้คือเคสที่ **หาไม่เจอด้วยการทดสอบผ่านหน้าจอ** เพราะหน้าจอรุ่นใหม่เขียนฟิลด์ถูกเสมอ ต้อง seed ข้อมูลรูปแบบเก่าเข้าไปทดสอบตรงๆ ถึงจะโผล่

## การแก้และการยืนยัน

แก้ทั้งสามชั้น แล้วรัน regression ชุดเดิมซ้ำ **8/8 ผ่าน** บนสภาพแวดล้อมจริง ครอบทั้ง 3 ผลลัพธ์ที่ต้องต่างกัน:

| สถานการณ์ | ผลที่ต้องได้ |
|---|---|
| ผู้ใช้องค์กรตัวเอง ทำงานปกติ | สำเร็จ |
| ไม่มี token | ปฏิเสธ (401) |
| token องค์กร A แตะข้อมูลองค์กร B | ปฏิเสธ (403) |

## บทเรียนที่เอาไปใช้ต่อ

- **การทดสอบความปลอดภัยคือการทดสอบสิ่งที่ "ต้องทำไม่ได้"** ชุดเทสที่มีแต่เคสสำเร็จ พิสูจน์ไม่ได้เลยว่าข้อมูลไม่รั่ว
- **อย่าเชื่อชั้นเดียว** ถ้าหน้าเว็บกรองให้แล้วเลยไม่ตรวจที่ API และคิดว่ากฎฐานข้อมูลเดี๋ยวก็กัน — สุดท้ายไม่มีใครกันจริง ผมตรวจทุกชั้นแยกกัน และเจอบั๊กครบทุกชั้นจริงๆ
- **ข้อมูลรุ่นเก่าคือพื้นที่เสี่ยงที่คนลืมทดสอบ** ระบบที่ migrate มาจะมีข้อมูลสองรูปแบบอยู่ร่วมกันเสมอ ต้อง seed ของเก่าเข้าไปทดสอบด้วย ไม่ใช่ทดสอบแต่ของที่ระบบปัจจุบันสร้าง
- **emulator ทำให้เทสความปลอดภัยรันได้ทุกครั้งที่ push** ไม่ต้องรอ pentest ปีละครั้ง และไม่ต้องเสี่ยงยิงระบบจริง
