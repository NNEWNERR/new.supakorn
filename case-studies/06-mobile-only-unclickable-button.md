# CS-06 · ปุ่มที่ "มองเห็น" แต่ "กดไม่ได้" และเกิดเฉพาะบนมือถือ

> **สรุปสั้น:** `toBeVisible()` ผ่าน ไม่ได้แปลว่าผู้ใช้กดได้
> เทสที่เช็คแค่ว่ามองเห็น จะปล่อยบั๊กประเภทนี้ผ่านไปทุกครั้ง

| | |
|---|---|
| **ระบบ** | แพลตฟอร์มจองคิวบริการ (Angular + Tailwind) |
| **บทบาทของผม** | ยืนยันอาการด้วย Playwright, หาสาเหตุ, แก้ CSS, ตรวจซ้ำทั้งสองขนาดจอ |
| **เทคนิคที่ใช้** | hit-testing (ไม่ใช่แค่ visibility), ทดสอบแยกตามขนาดหน้าจอ |

## อาการ

เปิดรายละเอียดงานขึ้นมาเป็น modal บนมือถือ แล้ว **ปุ่มย้อนกลับกดไม่ได้** — เห็นปุ่มอยู่ตรงนั้นชัดเจน กดแล้วไม่มีอะไรเกิดขึ้น บนจอคอมพิวเตอร์ปกติดี

## จุดที่เกือบพลาด

เทสที่เขียนไว้ตอนแรกเช็คว่า "ปุ่มแสดงผลอยู่" ซึ่ง**ผ่าน** เพราะปุ่มแสดงผลอยู่จริง — มันแค่มีของอื่นทับอยู่ข้างบน

เครื่องมือทดสอบส่วนใหญ่ถือว่า element ที่มีขนาด ไม่ถูกซ่อน และอยู่ในจอ = "มองเห็นได้" ซึ่งเป็นคนละเรื่องกับ **"คลิกแล้วโดน"** ต้องเปลี่ยนไปตรวจว่า *จุดกึ่งกลางของปุ่มนั้น เมื่อคลิกลงไปจริง ตัวที่รับคลิกคือปุ่มหรือเปล่า*

## สาเหตุราก

หน้าเพจมี animation เฟดเข้า ตั้งค่าให้ **ค้างสถานะสุดท้ายไว้หลังเล่นจบ**

CSS มีกฎว่า element ที่มี animation ค้างอยู่บน `opacity` จะกลายเป็น **stacking context** ของตัวเอง — และ "ค้างสถานะไว้" แปลว่ามันยังนับว่า animation มีผลอยู่ **ตลอดไป** ไม่ใช่แค่ตอนเล่น

ผลคือ:

```
<main>  ← animation ค้าง → กลายเป็นกล่อง z-index ปิดตายของตัวเอง
   └─ modal (z-50)      ค่า 50 มีความหมายแค่ "ภายในกล่องนี้" เท่านั้น
<topbar> (z-20)         อยู่นอกกล่อง จึงชนะ modal ที่อยู่ข้างใน
```

modal ที่ตั้ง z-index ไว้สูงกว่า **แพ้** แถบด้านบนที่ตั้งไว้ต่ำกว่า เพราะมันอยู่กันคนละกล่อง — ค่า z-index เทียบกันได้เฉพาะภายในกล่องเดียวกัน

**ทำไมเจอเฉพาะมือถือ:** บนจอคอมพิวเตอร์ modal กว้างและวางตำแหน่งไม่ทับกับแถบด้านบน พื้นที่ซ้อนทับจึงไม่ตกใส่ปุ่มไหน พอจอแคบลง modal ขยายเต็มจอ ปุ่มย้อนกลับเลื่อนไปอยู่ใต้แถบด้านบนพอดี

## การแก้

เอา "ค้างสถานะ" ออกจาก animation และตัด `transform` ออกจาก keyframes (`transform` สร้างปัญหาอีกชุดหนึ่ง คือทำให้ element ลูกที่เป็น `position: fixed` ยึดกับกล่องนี้แทนที่จะยึดกับหน้าจอ) เหลือแค่การเฟด opacity ซึ่งได้เอฟเฟกต์เดิมโดยไม่สร้างกล่องปิดตาย

## การยืนยัน

ทดสอบด้วย Playwright แบบ hit-test บนระบบจริง **ทั้งขนาดมือถือ (390px) และเดสก์ท็อป** — ยืนยันว่าจุดที่ผู้ใช้กด ตัวที่รับคลิกคือปุ่มย้อนกลับจริง ไม่ใช่แถบด้านบน

## บทเรียนที่เอาไปใช้ต่อ

- **"มองเห็น" กับ "กดได้" เป็นคนละคำถาม** บั๊กที่ element ถูกของอื่นทับ จะผ่านเทสที่เช็คแค่ visibility ทุกครั้ง ถ้าเป็นปุ่มสำคัญ ต้องตรวจว่าคลิกแล้วโดนจริง
- **ต้องทดสอบที่ขนาดจอมือถือแยกต่างหาก** ไม่ใช่ย่อหน้าต่างเบราว์เซอร์แล้วดูผ่านๆ — บั๊กนี้มีอยู่เฉพาะเมื่อ layout สลับไปโหมดแคบ
- **บั๊ก UI ที่ดูเหมือนเรื่องความสวยงาม อาจเป็นบั๊กที่บล็อกผู้ใช้จริง** ปุ่มย้อนกลับกดไม่ได้บนมือถือ = ผู้ใช้ติดอยู่ในหน้านั้น ความรุนแรงสูงกว่าที่หน้าตาของมันบอกมาก
