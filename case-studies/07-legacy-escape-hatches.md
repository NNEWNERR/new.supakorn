# CS-07 · ช่องทางลัดของระบบรุ่นเก่าที่ลืมปิด — คนไม่ล็อกอินอ่านข้อมูลลูกค้าได้ทั้งหมด

> **สรุปสั้น:** ระบบเลิกใช้เวอร์ชันเก่าไปแล้ว 3 เดือน แต่ "สิทธิ์พิเศษ" ที่เปิดไว้ให้เวอร์ชันเก่า
> ยังอยู่ครบ — และช่องที่อันตรายที่สุดไม่ได้เปิดให้คนไม่ล็อกอิน แต่เปิดให้ **คนที่ล็อกอินแล้ว
> แต่ยังไม่มีสังกัด** ซึ่งใครก็สมัครเอาเองได้

| | |
|---|---|
| **ระบบ** | แพลตฟอร์มจองคิวบริการแบบ multi-tenant (หลายองค์กรใช้ฐานข้อมูลร่วมกัน) ใช้งานจริง |
| **บทบาทของผม** | ตรวจสิทธิ์การเข้าถึงข้อมูล, เขียน rules test พิสูจน์, แก้กฎ, ตรวจซ้ำบน production |
| **เทคนิคที่ใช้** | security rules review, negative testing, mutation check, blast-radius analysis |

## บริบท

ระบบเคยมีเว็บสองเวอร์ชันใช้ฐานข้อมูลเดียวกัน ตอนย้ายมาเวอร์ชันใหม่จึงเปิด "ทางผ่าน" ไว้ในกฎความปลอดภัยของฐานข้อมูล เพื่อให้เวอร์ชันเก่าที่ยังไม่มีระบบ token ทำงานต่อได้ พร้อมคอมเมนต์กำกับว่า *ลบเมื่อปิดเวอร์ชันเก่า*

เวอร์ชันเก่าถูกปิดไปตามแผน แต่ทางผ่านยังอยู่ ไม่มีใครกลับมาลบ เพราะมันไม่ทำให้อะไรพัง — **โค้ดที่ให้สิทธิ์เกินจำเป็นไม่เคยส่งเสียงร้อง**

## สิ่งที่พบ

อ่านกฎทีละบรรทัดแล้วถามคำถามเดียวกับทุกเงื่อนไข: *ใครบ้างที่เข้าเงื่อนไขนี้ได้ในวันนี้*

**ช่องที่ 1 — คนไม่ล็อกอิน**

- อ่าน **งานทั้งหมด** ของร้านหลักได้ ซึ่งมีชื่อ เบอร์โทร และที่อยู่ของลูกค้าทุกคน
- **สร้างงานเองได้โดยตรง** ข้ามการตรวจคิวว่าง ข้ามการตรวจโควตา ข้ามการตรวจความถูกต้องทั้งหมด เพราะเส้นทางปกติต้องผ่านฟังก์ชันฝั่ง server

**ช่องที่ 2 — คนที่ล็อกอินแล้วแต่ยังไม่มีสังกัด (อันตรายกว่า)**

กฎข้อนี้เขียนไว้ว่า "ผู้ใช้ที่ยืนยันเบอร์โทรแล้วแต่ยังไม่มีข้อมูลสังกัด" ให้สิทธิ์ **อ่านข้อมูลทุกองค์กรบนแพลตฟอร์ม** ทั้งงาน รายชื่อผู้ใช้ ข้อมูลลูกค้า และประกาศ

ตอนเขียนกฎนี้ ผู้ใช้กลุ่มนั้นคือพนักงานที่ล็อกอินด้วยเบอร์โทรในระบบเก่า แต่หลังย้ายไปใช้รหัสผ่าน **กลุ่มเดียวที่เหลืออยู่ในเงื่อนไขนี้คือคนที่กำลังสมัครสมาชิกใหม่** — และหน้าสมัครสมาชิกเปิดให้ทุกคน

**ใครก็ได้ที่มีเบอร์โทร กดขอรหัส OTP ด้วยเบอร์ตัวเองในหน้าสมัคร แล้วเอา token ช่วงนั้นไปดึงข้อมูลลูกค้าของทุกร้านบนแพลตฟอร์มได้ โดยไม่ต้องสมัครให้จบด้วยซ้ำ**

## พิสูจน์ก่อนแก้

ก่อนแตะกฎ ต้องตอบให้ได้สองข้อ: **ช่องนี้เปิดจริงไหม** และ **ปิดแล้วอะไรพัง**

ชุดทดสอบกฎบน emulator ที่มีอยู่แล้ว 90 เคส ตอบข้อแรกให้ทันที เพราะมีเคสที่เขียนไว้ตั้งแต่ยุคก่อนว่า *"ผู้ใช้เบอร์โทรอ่านงานได้ทุกใบ → allow"* — เคสนั้นไม่ใช่เอกสารของพฤติกรรมที่ต้องการ แต่เป็น**หลักฐานว่าช่องโหว่มีอยู่จริงและถูกล็อกไว้ด้วยเทส**

ข้อสองตอบด้วยการไล่โค้ดฝั่งหน้าเว็บว่าใครยังพึ่งสิทธิ์พวกนี้อยู่: ลูกค้าดูงานผ่านฟังก์ชันฝั่ง server, การจองผ่านฟังก์ชันฝั่ง server, พนักงานล็อกอินด้วยรหัสผ่านและมี token ที่ระบุสังกัดแล้ว — **ไม่มีใครใช้ทางผ่านนี้อีกเลย** เหลือแค่ข้อมูลสาธารณะอย่างรายการสาขาและราคาที่หน้าจองต้องอ่านได้ตอนยังไม่ล็อกอิน

## การแก้

- ปิดการอ่านและสร้างงานสำหรับผู้ใช้ที่ไม่มีสังกัดทั้งหมด การสร้างงานจากฝั่ง client กลายเป็น "ไม่อนุญาต" อย่างเดียว
- ลบเงื่อนไข "ผู้ใช้เบอร์โทรที่ยังไม่มีสังกัด" ออกจากทุก collection
- เปลี่ยนตัวช่วยในกฎจาก "ยังไม่ล็อกอิน" เป็น **"ไม่มีข้อมูลสังกัด"** แล้วให้สิทธิ์เฉพาะข้อมูลสาธารณะที่หน้าจองต้องใช้

จุดสุดท้ายคือหัวใจ: ถ้าเขียนเงื่อนไขว่า "ยังไม่ล็อกอิน" คนที่ล็อกอินแล้วจะได้สิทธิ์**มากกว่า**คนที่ไม่ล็อกอิน ทั้งที่การได้ session มาเป็นเรื่องง่ายที่สุด เพราะหน้าสมัครแจกให้อยู่แล้ว **เส้นแบ่งที่ถูกต้องคือ "มีสังกัดหรือยัง" ไม่ใช่ "ล็อกอินหรือยัง"**

## การยืนยัน

| วิธี | ผล |
|---|---|
| ชุดทดสอบกฎบน emulator | 90/90 ผ่านบนกฎใหม่ · **แดง 15 เคสบนกฎเดิม** (รวมเคสที่พิสูจน์ว่า token จากหน้าสมัครอ่านงานขององค์กรอื่นได้) |
| ยิง REST ตรงไปฐานข้อมูลแบบไม่ล็อกอิน | อ่านงาน / ผู้ใช้ / ลูกค้า และสร้างงาน = ถูกปฏิเสธทั้งหมด · อ่านสาขาและราคา = ยังได้ |
| ชุด E2E บน CI | เขียวครบทุกชุด |
| ทดสอบด้วยมือบน production | พนักงานล็อกอิน เปิดตารางงาน เปลี่ยนสถานะงาน ได้ตามปกติ |

"แดง 15 เคสบนกฎเดิม" คือตัวเลขที่มีค่าที่สุดในตารางนี้ เพราะมันพิสูจน์ว่าเทสชุดนี้**จับของจริงได้** ไม่ใช่ผ่านเพราะกฎอะไรก็ได้

## ผลกระทบลูกโซ่ที่ตามมา — และทำไมมันคือข่าวดี

ปิดช่องเสร็จ มีสองอย่างพังทันที ทั้งคู่มีค่ามากกว่าที่คิด

**1. หน้าเว็บสาธารณะขึ้น error ใน console ทุกครั้งที่เปิด** แอปเปิดการเชื่อมต่อเพื่อนับ "งานรอดำเนินการ" ให้ **ทุกคน** ทั้งที่ตัวเลขนั้นเป็นป้ายแจ้งเตือนของพนักงานเท่านั้น คนทั่วไปไม่เคยเห็น แก้โดยผูกการเชื่อมต่อนั้นกับสิทธิ์ผู้ใช้ — ได้ลดการอ่านฐานข้อมูลที่ไม่มีใครใช้ไปด้วย

**2. เทสที่ "โกหก" มาตลอดถูกจับได้** ชุด E2E ของพนักงานหลอก session ลงไปใน `localStorage` ตรงๆ โดยไม่ล็อกอินจริง ซึ่งทำงานได้เพราะกฎเดิมเปิดให้ session ปลอมอ่านข้อมูลได้ พอปิดช่อง เทสกลุ่มนี้ก็ถูกเด้งออกไปหน้าล็อกอิน

เทสพวกนี้ "ผ่าน" มาตลอดโดยทดสอบสถานะที่**เกิดขึ้นจริงไม่ได้บน production** เพราะผู้ใช้จริงต้องมี session ของระบบยืนยันตัวตนเสมอ แก้โดยให้ล็อกอินจริงผ่านหน้าจอ แล้วรับ secret จาก CI

**และยังทำให้เจอบั๊กจริงเพิ่มอีกหนึ่ง** เทสที่ตรวจว่า "session ที่อ้างถึงผู้ใช้ที่ไม่มีอยู่จริง ต้องถูกล้างแล้วเด้งไปหน้าล็อกอิน" เปลี่ยนเป็นแดง เพราะโค้ดตรวจ session ดักทุก error แล้วถือว่า "ผ่าน" — เดิมทำงานถูกเพราะอ่านข้อมูลผู้ใช้ได้ พอปิดช่องแล้วการอ่านถูกปฏิเสธ จึงกลายเป็นว่าผู้ใช้ที่ session หมดอายุจะ**ค้างอยู่ในหน้าหลังบ้านที่โหลดอะไรไม่ขึ้นเลย** แทนที่จะถูกพากลับไปล็อกอิน

แก้โดยล้าง session เฉพาะเมื่อพิสูจน์ได้ว่าไม่มี session จริงรองรับ **ไม่ใช่ล้างทุกครั้งที่อ่านพลาด** เพราะจังหวะหลังล็อกอินใหม่ๆ สิทธิ์ยังกระจายไม่ครบ ถ้าล้างทันทีจะกลายเป็นบั๊ก "ล็อกอินแล้วหลุดแบบสุ่ม" ที่เคยแก้ไปแล้วใน [CS-01](01-auth-race-condition.md)

## บทเรียนที่เอาไปใช้ต่อ

- **คอมเมนต์ว่า "ลบเมื่อ X" ไม่ใช่แผน** ถ้าไม่มีใครถือวันครบกำหนด สิทธิ์ชั่วคราวจะกลายเป็นสิทธิ์ถาวรเสมอ ตอนปิดฟีเจอร์เก่าต้องมีรายการสิทธิ์ที่ต้องปิดตามไปด้วย
- **ถามว่า "วันนี้ใครเข้าเงื่อนไขนี้ได้" ไม่ใช่ "ตอนเขียนเจตนาให้ใคร"** เงื่อนไขไม่เปลี่ยน แต่คนที่เข้าเงื่อนไขเปลี่ยนตลอดเวลา — โดยเฉพาะหลังย้ายระบบล็อกอิน
- **เส้นแบ่งสิทธิ์ต้องเป็นสิ่งที่ผู้ใช้ทั่วไปสร้างเองไม่ได้** "ล็อกอินแล้ว" เป็นสิ่งที่ใครก็ทำได้ จึงใช้เป็นเส้นแบ่งไม่ได้ ต้องใช้ข้อมูลที่ระบบเป็นคนให้เท่านั้น
- **เทสที่ผ่านตลอดอาจกำลังทดสอบสถานะที่ไม่มีจริง** การหลอก session ให้เทสสะดวกขึ้น แลกมาด้วยการที่เทสไม่ได้ตรวจเส้นทางที่ผู้ใช้จริงเดิน
- **การแก้ความปลอดภัยที่ดีจะทำให้ของพัง** และของที่พังมักคือของที่พึ่งสิทธิ์เกินจำเป็นอยู่ ถ้าปิดช่องแล้วไม่มีอะไรพังเลย ควรกลับไปตรวจว่าปิดได้จริงหรือเปล่า
