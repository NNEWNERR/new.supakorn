# CS-08 · เทสฟ้องว่า "จองซ้อนได้" ทั้งที่ระบบถูก — บั๊กของเทสซ้อนกัน 4 ชั้น

> **สรุปสั้น:** เทสที่พิสูจน์ว่า "สองคนจองคิวเดียวกันพร้อมกัน ต้องผ่านได้คนเดียว"
> แดงสลับเขียวเป็นเดือน บางครั้งฟ้องว่า **ผ่านทั้งคู่** ซึ่งถ้าจริงคือบั๊กร้ายแรงที่สุดของระบบจอง
> สุดท้ายระบบถูกต้อง 13 จาก 13 ครั้ง — ที่ผิดคือเทสเอง ทีละชั้น รวม 4 ชั้น

| | |
|---|---|
| **ระบบ** | แพลตฟอร์มจองคิวบริการ ใช้งานจริง (ธุรกรรมแบบ atomic ป้องกันการจองซ้อน) |
| **บทบาทของผม** | ไล่หาสาเหตุ, แยกให้ออกว่าปัญหาอยู่ที่ระบบหรือที่เทส, เขียนเทสใหม่, ยืนยัน |
| **เทคนิคที่ใช้** | isolate the system under test, direct API probing, event-driven assertion, test-data isolation |

## อาการ

เทส "สอง context กดจองคิวเดียวกันพร้อมกัน → ต้องสำเร็จแค่รายเดียว" แดงประมาณครึ่งต่อครึ่ง และรูปแบบการแดงไม่เหมือนกันสักครั้ง

- บางครั้ง **สำเร็จทั้งคู่** — ถ้าเป็นเรื่องจริง แปลว่าลูกค้าสองคนได้คิวเดียวกัน
- บางครั้ง **ล้มทั้งคู่**
- บางครั้งได้ผลถูกต้อง แต่เทสยังแดง

**จุดที่ต้องตัดสินใจก่อนทุกอย่าง:** เคสนี้ห้ามใส่ retry แล้วปล่อยผ่านเด็ดขาด เพราะถ้าระบบจองซ้อนได้จริง นั่นคือบั๊กที่ทำให้ช่างไปถึงหน้างานแล้วเจอลูกค้าสองเจ้า

## ขั้นแรก — แยกระบบออกจากเทส

แทนที่จะไล่แก้เทสไปเรื่อยๆ ผมตัดหน้าเว็บทิ้งทั้งหมด แล้ว**ยิงตรงไปที่ฟังก์ชันจองฝั่ง server แบบขนานสองคำขอ ด้วยข้อมูลเหมือนกันเป๊ะ** วนซ้ำ 13 รอบ

ผลคือ **1 สำเร็จ + 1 ถูกปฏิเสธ ทุกรอบ ไม่มีข้อยกเว้น**

คำถามเปลี่ยนทันทีจาก "ระบบจองซ้อนได้ไหม" เป็น "**ทำไมสองหน้าจอถึงไม่ได้ชนกันจริง**" ซึ่งเป็นคำถามที่ตอบได้

## สาเหตุ — ทีละชั้น

**ชั้นที่ 1: สอง context เลือกคนละสาขา** หน้าจองแบบสาธารณะเลือกสาขาเริ่มต้นเป็น "สาขาแรกในรายการ" ณ วินาทีที่ข้อมูลชุดแรกมาถึง ถ้าข้อมูลมาไม่พร้อมกัน สอง context จะได้คนละสาขา → คนละคิว → **จองสำเร็จทั้งคู่อย่างถูกต้อง** แล้วเทสก็ฟ้องว่าระบบพัง

แก้โดยเข้าหน้าจองผ่านลิงก์ QR ที่ล็อกสาขาไว้ใน URL

**ชั้นที่ 2: ตัวช่วยเลือกวันที่คลิกผิดวัน** ฟังก์ชันเลือกวันในปฏิทินกดปุ่ม "เดือนถัดไป" รัวโดยไม่รอให้หน้าจอวาดเดือนใหม่เสร็จ พอสั่งวันเดียวกันทั้งสอง context กลับได้คนละวัน — จับได้เพราะเพิ่มการเทียบ "สรุปการจอง" ของทั้งสองหน้าก่อนกดยืนยัน แล้วเห็นว่าวันไม่ตรงกัน

แก้โดยรอให้หัวปฏิทินเปลี่ยนจริงก่อนกดต่อ และ**ตรวจซ้ำหลังเลือกว่าได้วันที่สั่งไปจริงไหม** ถ้าพลาดให้ฟ้องว่า "เลือกวันผิด" ทันที ไม่ใช่ปล่อยให้ไปพังที่ขั้นอื่น

**ชั้นที่ 3: ข้อความ error ของฝั่งที่แพ้หายไปก่อนเทสไปดู** ฝั่งที่จองไม่สำเร็จแสดงข้อความแบบ toast ที่หายเอง แต่เทสนอนรอ 3 วินาทีแล้วค่อยไปอ่าน บางครั้งไปถึงตอนข้อความหายแล้ว

แก้โดยเปลี่ยนเป็นรอผลแบบ event-driven: แข่งกันระหว่าง "ไปถึงหน้าสำเร็จ" กับ "ข้อความ error โผล่" ใครมาก่อนคือผลลัพธ์ ไม่ต้องเดาเวลา

**ชั้นที่ 4: เทสไปชนคิวจริงของร้าน และชนกันเอง** วันที่สุ่มอยู่ในช่วง 30–90 วันข้างหน้า ซึ่งมีคิวจริงของลูกค้าอยู่ → ถูกปฏิเสธทั้งคู่ และทุกเทสเลือก "ชั่วโมงแรกที่ว่าง" เหมือนกันหมด คือ 09:00 งานทดสอบจึงกองอยู่ที่ชั่วโมงเดียวจนเต็มโควตา

ซ้ำร้าย ทุกเทสยัง**ล้างข้อมูลทดสอบด้วยเงื่อนไขกว้างเกินไป** คือลบงานที่เบอร์ขึ้นต้นด้วยรหัสทดสอบ *ทั้งหมด* ทำให้เทสที่รันขนานกันลบข้อมูลของกันเองกลางคัน

แก้ทั้งชุด: จองไกลออกไป 150–210 วัน, สุ่มชั่วโมงแทนการเอาชั่วโมงแรก, และให้แต่ละเทสล้างเฉพาะข้อมูลที่ตัวเองสร้าง

## สิ่งที่ได้มาระหว่างทาง

**เรื่องของระบบที่ไม่ใช่บั๊กแต่ควรรู้:** ปุ่มเลือกเวลาบนหน้าจองสะท้อน "โควตาของกลุ่มช่าง" ไม่ได้บอกว่าสาขานั้นถูกจองชั่วโมงนั้นไปแล้วหรือยัง ลูกค้าจึงเลือกเวลาที่ดูว่างได้ แล้วโดนปฏิเสธตอนกดยืนยัน — ไม่ใช่ข้อผิดพลาดของโค้ด แต่เป็นจุดที่ประสบการณ์ผู้ใช้สะดุด และถูกบันทึกไว้เป็นข้อเสนอแยก

**เรื่องของเทสที่กระทบทั้งชุด:** ตัวช่วยเลือกวันที่คลิกผิดถูกใช้ร่วมกันเกือบทุกไฟล์เทส การคลิกพลาดจึงทำให้เทสอื่นฟ้องผิดจุดได้อีกหลายที่ ตอนนี้ถ้าเลือกวันพลาดจะฟ้องว่า "เลือกวันผิด" ทันที

## การยืนยัน

- ยิงฟังก์ชันจองแบบขนาน **13/13 รอบ ได้ 1 สำเร็จ + 1 ถูกปฏิเสธ** ทุกครั้ง
- เทสรันบน CI ผ่านตั้งแต่ครั้งแรกโดยไม่ต้องพึ่ง retry
- ขยายชุดเทสบน CI จาก 7 ชุดเป็น 17 ชุด และเขียวทั้งหมด

## บทเรียนที่เอาไปใช้ต่อ

- **เทสที่ฟ้องบั๊กร้ายแรง ต้องพิสูจน์ที่ระบบก่อนเสมอ** วิธีเร็วที่สุดคือตัดหน้าเว็บทิ้งแล้วยิงตรงไปที่ API — ถ้าระบบถูก คำถามจะเปลี่ยนเป็น "เทสผิดตรงไหน" ซึ่งตอบง่ายกว่ามาก
- **เทสที่แดงสลับเขียวมักมีหลายสาเหตุซ้อนกัน** แก้ชั้นแรกแล้วยังแดง ไม่ได้แปลว่าแก้ผิด แต่แปลว่ามีอีกชั้น ถ้าใส่ retry ตั้งแต่ชั้นแรกจะไม่มีวันเห็นอีกสามชั้น
- **ทำให้เทสฟ้องสาเหตุจริง ไม่ใช่ timeout** เดิมเทสรายงานว่า "รอเปลี่ยนหน้าไม่สำเร็จ" ซึ่งไม่บอกอะไรเลย พอเปลี่ยนให้แสดงข้อความจากระบบ สาเหตุก็โผล่ทันทีว่าเป็นคิวเต็มหรือสาขาถูกจอง
- **เทสที่ใช้ข้อมูลจริงร่วมกัน ต้องออกแบบให้ไม่ชนกัน** ทั้งกับข้อมูลของผู้ใช้จริง และกับเทสตัวอื่นที่รันพร้อมกัน การล้างข้อมูลด้วยเงื่อนไขกว้างๆ คือการทำลายของคนอื่นโดยไม่รู้ตัว
- **การตรวจสมมติฐานก่อนวัดผล ทำให้เทสฟ้องถูกจุด** เทียบว่าสอง context เล็งคิวเดียวกันจริงก่อนกดจอง เปลี่ยนคำฟ้องจาก "ระบบจองซ้อนได้" เป็น "เทสเล็งคนละคิว" ซึ่งต่างกันคนละเรื่อง
