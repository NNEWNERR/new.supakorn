# Case Studies — บั๊กจริงจากระบบที่ใช้งานอยู่

งานบางส่วนของผมอยู่ในระบบที่ใช้งานจริงและ repo เป็น private — เอาโค้ดมาแสดงไม่ได้
แต่**วิธีคิดตอนไล่หาสาเหตุ**เอามาเล่าได้ และนั่นคือส่วนที่มีค่ากว่าโค้ด

แต่ละเคสเล่าตามลำดับเดียวกัน: อาการที่เห็น → วิธีตามรอย → สาเหตุราก → การแก้ →
การยืนยัน → บทเรียน โดยไม่มีข้อมูลลูกค้า ชื่อระบบภายใน หรือค่า config ใดๆ

| เคส | เรื่อง | เทคนิคหลัก |
|---|---|---|
| [CS-01](01-auth-race-condition.md) | login ล้มแบบสุ่ม 1 ใน N ครั้ง — race condition ระหว่าง session สองเส้น | แยกให้ออกว่า "เทสไม่นิ่ง" หรือ "ระบบไม่นิ่ง" ก่อนใส่ retry |
| [CS-02](02-role-silent-failures.md) | เพิ่ม role ใหม่ 1 ตัว พังเงียบ 6 จุด | decision table (role × หน้าจอ), เคส refresh / deep link |
| [CS-03](03-slot-leak.md) | คิวเต็มทั้งที่งานยกเลิกแล้ว — ที่นั่งค้าง 640 รายการ | state-transition testing, remediation แบบ idempotent |
| [CS-04](04-tenant-isolation.md) | กันข้อมูลข้ามองค์กรรั่ว — ทดสอบ 3 ชั้น เจอบั๊กครบ 3 ชั้น | negative testing, rules test บน emulator (91 เคส), defense in depth |
| [CS-05](05-zombie-service-worker.md) | deploy แล้วบางเครื่องเห็นหน้าเก่า — service worker ที่ตายไม่ลง | แยกตัวแปรด้วย incognito, ยืนยันที่ HTTP header |
| [CS-06](06-mobile-only-unclickable-button.md) | ปุ่มที่ "มองเห็น" แต่ "กดไม่ได้" และเกิดเฉพาะบนมือถือ | hit-testing แทน visibility, ทดสอบแยกตามขนาดจอ |

## เส้นที่ร้อยทั้งสามเคส

- **บั๊กที่ "เจอบ้างไม่เจอบ้าง" คือบั๊กที่ต้องสืบ ไม่ใช่บั๊กที่ต้องกลบ** — CS-01
- **ถามเสมอว่าขอบเขตกระทบจริงกว้างแค่ไหน** บั๊กที่โผล่ใน flow ใหม่ มักไม่ใช่บั๊กของ flow ใหม่ — CS-01, CS-02
- **ข้อเสนอของ QA ควรรวมถึง "แก้ยังไงไม่ให้กลับมาอีก"** ไม่ใช่แค่ชี้ว่าตรงไหนผิด — CS-02, CS-03
- **เส้นทางย้อนกลับ (ยกเลิก / ปฏิเสธ / refresh) คือที่ที่บั๊กชอบอยู่** เพราะการทดสอบด้วยมือมักไล่แต่เส้นตรง — CS-02, CS-03
- **ยืนยันด้วยสิ่งที่วัดได้ ไม่ใช่ด้วยสายตา** header ที่ตอบกลับมา, ตัวที่รับคลิกจริง, ผลลัพธ์ที่ต้องถูกปฏิเสธ — CS-04, CS-05, CS-06
- **"ผ่าน" ของเครื่องมือ ไม่เท่ากับ "ใช้งานได้" ของผู้ใช้** เทสที่เช็คว่ามองเห็น ปล่อยปุ่มที่กดไม่ได้ผ่านไปได้ — CS-06
