## Test Design & QA Practice
- ออกแบบเคสด้วย **decision table (role × หน้าจอ)** ตอนระบบเพิ่ม role ใหม่เพียง 1 ตัว
  พบจุดที่พังเงียบ 6 จุด รวมเส้นทาง refresh และ deep link ที่การไล่คลิกตามปกติไม่โดน
- ใช้ **state-transition testing** กับเส้นทางยกเลิก พบที่นั่งค้างในคิว 640 รายการ
  แล้วเสนอวิธีล้างข้อมูลแบบ idempotent ไปพร้อมกับรายงานบั๊ก
- วาง **negative testing 3 ชั้น** สำหรับการกันข้อมูลข้ามองค์กร เจอช่องรั่วครบทั้ง 3 ชั้น
  และยืนยันผลด้วยชุดทดสอบกฎสิทธิ์ 90 เคสบน emulator จริง
- แยก **"เทสไม่นิ่ง" ออกจาก "ระบบไม่นิ่ง" ก่อนใส่ retry** — เคส login ล้มแบบสุ่ม
  สืบจนพบว่าเป็น race condition ระหว่าง session สองเส้น ไม่ใช่เทสที่ต้องกลบด้วย retry
- พิสูจน์ว่า **เทสฟ้องผิด ไม่ใช่ระบบผิด** โดยตัด UI ออกแล้วยิง API ตรง
  เปลี่ยนข้อกล่าวหา "จองซ้อนได้" ให้เป็นคำถามที่ตอบได้ ปลายทางเป็นบั๊กของเทสเอง 4 ชั้น
- ใช้ **hit-testing แทนการเช็ค visibility** กับปุ่มที่ "มองเห็นแต่กดไม่ได้" และเกิดเฉพาะบนมือถือ
  เพราะ "ผ่าน" ของเครื่องมือไม่เท่ากับ "ใช้งานได้" ของผู้ใช้
- เขียน **bug report 8 เคส** ตามโครงเดียวกันทุกเคส: อาการที่เห็น → วิธีตามรอย → สาเหตุราก →
  การแก้ → การยืนยัน → บทเรียน เผยแพร่ได้โดยไม่มีข้อมูลลูกค้าหรือค่า config
  (new.supakorn/case-studies)
- ติดกำกับทุกเทสใน repo qa-automation ว่าใช้เทคนิคอะไรและเพราะอะไร
  (equivalence partitioning, boundary, decision table, state transition)
