## Test Design & QA Practice
- ออกแบบ 24 เคสสำหรับเส้นแบ่งสิทธิ์จุดเดียว (ชุด `public-boundary`) จนสรุปได้ว่ากฎจริงคือ "ผู้ใช้ยังไม่มีสังกัด" ไม่ใช่ "ผู้ใช้ยังไม่ล็อกอิน" ซึ่งเป็นจุดที่ requirement เดิมกำกวม
- เขียนรายงานบั๊ก 8 เคสจากแพลตฟอร์มจองคิวที่ใช้งานจริง เป็น case study ที่ไล่ อาการ → วิธีทำซ้ำ → สาเหตุราก ให้ developer เอาไปแก้ได้โดยไม่ต้องย้อนมาถามอีกรอบ ได้แก่ auth race condition, role ที่ล้มเหลวแบบเงียบ, slot การจองรั่ว, ช่องโหว่การแยกข้อมูลระหว่าง tenant, service worker ค้างเสิร์ฟโค้ดที่ตายแล้ว, ปุ่มที่กดได้แต่บน desktop, ข้อมูลรุ่นเก่าที่หลุดกฎใหม่ และอีกหนึ่งเคสที่เทสผิดเองโดยระบบถูก
- บันทึกกำกับทุกเทสใน README ของ `qa-automation` ว่าใช้เทคนิคอะไรและเพราะอะไร — equivalence partitioning, boundary, decision table, state transition — ให้การเลือกเคสถูกรีวิวได้ ไม่ใช่ความเคยชินส่วนตัว
- เขียน 90 เคสเรื่องสิทธิ์ที่ assert ว่าระบบ **ต้องปฏิเสธ** อะไร หลังจากเจอว่า "ใช้ได้ตอนเป็น admin" ไม่ได้บอกอะไรเลยว่าคนที่ยังไม่ล็อกอินเข้าถึงอะไรได้
- เขียน `TESTING.md` เอกสารกลยุทธ์การทดสอบที่มีขอบเขต, risk matrix และ test pyramid เพื่อตัดสินความครอบคลุมด้วยความเสี่ยง ไม่ใช่ด้วยความง่ายในการทดสอบ
- ยืนยันให้บันทึกความล้มเหลวที่เกิดเป็นครั้งคราวจาก dependency ภายนอกไว้ให้ชัด ไม่กลบด้วย retry เพราะ retry ที่ใส่เพื่อให้รันผ่านจะบังบั๊กจริงตัวถัดไปในเทสตัวเดียวกัน

## Automation Toolkit
มีไว้ให้ใช้เมื่อทีมต้องการ และคุ้มกับงาน regression ที่ไม่อย่างนั้นต้องกดซ้ำด้วยมือ:
Playwright กับ TypeScript (358 tests ใน 4 โปรเจกต์, 10 Page Object), Selenium, API testing ด้วย Postman,
accessibility check ด้วย axe-core และ GitHub Actions pipeline รวมถึงชุดที่รันกับ production ทุกวัน
ซึ่งรายงาน regression ได้ภายใน 24 ชั่วโมง เริ่มจาก manual ก่อนได้ แล้วค่อย automate ชุดที่คุ้มจะทำ
